# 数据所有权与 SQL 迁移管理规范

本规范适用于 Compass 全部 app 及其 SDD 需求。统一数据归属、迁移源、完整 SQL、增量 SQL、发布顺序与验收要求；各 app 可以拥有独立数据库实例，并选择适合其语言的迁移工具。需求工作区入口见 [mai-specs](../mai-specs/README.md)，应用入口见 [apps](../apps/README.md)。

## 1. 应用职责与数据库所有权

| 应用     | 负责的业务与权威数据                                                                                         | 数据访问边界                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `web`    | 产品 UI / BFF；账户映射、租户、成员、角色、权限、Web 会话、通用系统与租户配置等工程 CRUD                     | 在服务端直接读写自有数据库；浏览器不持有数据库凭据；通过 API 调用其他 app 的业务             |
| `agent`  | Agent Runtime、推理与工具执行、分析任务、Run / Step / Event、运行证据、报告/看板业务对象、执行预算及运行配置 | 直接读写自有数据库；向 Web 核验当前身份权限；通过受限接口访问分析数据源；文件内容引用 Memory |
| `memory` | 通用文件上传/存储/版本、正文/表格/元信息解析、OCR、主动字段/记忆候选抽取与确认；知识文档、记忆及其生命周期   | 独立存储和迁移；向 Web 核验身份权限，向资源所有者核验来源                                    |
| `worker` | 按需承载后台执行和任务消费                                                                                   | 执行位置不改变数据所有者；默认通过所有者 API 提交业务状态；若需自有调度状态，另行登记数据库  |
| `home`   | 官网、课程指南与静态分发                                                                                     | 当前无需业务数据库；出现持久化需求时重新确定数据所有者                                       |

归属依据是业务语义、状态生命周期和一致性边界。账户、权限及通用配置由 Web 直接实现；Runtime 的模型路由、工具能力与运行策略由 Agent 管理。管理页面位于 Web，不自动改变被管理对象的所有者。Web 中的普通 CRUD 无需经 Agent 转发；模型与工具执行仍由 Agent 负责。

2026-10-25 文件职责补充来自 [995 的用户范围记录](../mai-specs/995-web-management-foundation/context/_INDEX.md#2026-10-25-补充与范围纠正)：Memory 拥有通用文件内容与处理状态，Agent 拥有业务报告/看板和文件版本引用。Memory 内部为解析或主动抽取调用模型属于其领域实现，Agent 分析执行仍归 Agent。具体文件契约、引用授权与删除传播由后续业务 Feature 设计；995 本期只实现 Web 基座与页面框架，不交付 Memory 服务能力。

每张权威表只有一个 owner。跨 app 禁止直接查询或修改对方业务表、跨 app ORM 导入、数据库外键、跨库 JOIN 和分布式事务假设；使用带租户与版本的逻辑 ID、API 或已定义事件。消费者可保存可重建投影或执行快照，须标明来源、版本和失效规则，不能形成第二个写入权威。

Web 提供当前成员与授权核验契约；Agent / Memory 仍校验委托身份及自身资源、动作与状态，不接受浏览器声明的角色作为权限。授权核验失败时拒绝相关操作。跨服务撤权、缓存失效和高风险执行前复核必须在相关 Feature 中定义并验收，不能用跨库锁实现。Memory 管理页可由 BFF 直接调用 Memory；运行中的 Memory Tools 由 Agent / Worker 调用。

## 2. 管理单位与当前登记

迁移单位为 **`<app>/<database-key>`**。database-key 是稳定逻辑名称，与开发、测试、生产的主机、数据库名称及密码分离。同一 app 的多个库使用不同 key；每个单位独立拥有迁移历史、版本表、连接配置、迁移凭据和运行凭据。

独立实例、同实例不同 database、同 database 不同 schema 均可按部署需求采用；共享实例不授予跨 app 访问权。同库方案须隔离 schema、权限、版本表和对象解析路径。数据库实例、账号和基础权限由部署流程创建；应用迁移只操作已授权的自有对象，不在 SQL 中硬编码环境连接或密码。

| 单位               | 当前事实                              | 迁移源 / 入口                                                                              | 待接入内容                                    |
| ------------------ | ------------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------- |
| `agent/main`       | 已有演示应用库                        | [Alembic migrations](../apps/agent/migrations/)、`pnpm db:migrate`                         | 完整与增量 SQL 导出、差异检查与升级验证入口   |
| `data-seed/retail` | 998 独立教学数据候选库                | [工具迁移](../tools/data-seed/migrations/)、[数据操作流程](data-seeding.md)                | 沿用不可变数据包与候选发布，见 §8             |
| `web/main`         | 995 的 8 张业务表；独立 PostgreSQL 17 | [node-pg-migrate 原生 SQL 与交付](../apps/web/db/main/README.md)、`pnpm db:migrate -F web` | 后续真实版本再追加迁移                        |
| `memory/main`      | 当前仅健康检查                        | 首个文件/记忆持久化 Feature 登记工具、源路径和真实命令                                     | 文件/知识/记忆数据、独立连接、迁移与 SQL 交付 |
| `worker` / `home`  | 当前无自有业务库                      | 无                                                                                         | 确有持久化需求再登记，不创建空目录            |

当前 `pnpm db:migrate` 执行 Web 与 Agent 已登记的迁移；以 `-F web` / `-F agent` 明确目标，各库独立事务。`pnpm contracts` 管理 HTTP 契约，不负责数据库迁移。首次接入与后续入口变更须同步本表、所属 app README、根命令说明和相关 manifest。

零售教学源由离线工具 `data-seed` 管理，owner 为 `data-seed/retail`；Agent 只作为分析消费者。其候选库迁移位于 `tools/data-seed/migrations/`，不参与 `pnpm db:migrate`。本次只迁移代码归属，保留 revision、版本表、DDL 字节和既有数据库。

## 3. 目录与唯一源

新接入数据库采用以下布局；仅在实际交付时创建文件：

```text
apps/<app>/db/<database-key>/
├── README.md                         # 所有者、工具、源路径、配置名、真实命令
├── migrations/                       # 工具原生迁移源；SQL 或 Python / TS 等
└── sql/
    ├── bootstrap.sql                 # 空库初始化到明确目标版本
    └── upgrades/
        └── <from>__<to>.sql           # 固定版本区间的增量交付

mai-specs/NNN-<slug>/
├── design/TECH_DESIGN.md              # 数据归属、变更设计、迁移计划和源链接
└── IMPLEMENTATION.md                 # 交付文件、版本、执行与验证证据
```

上述 Feature 路径沿用默认值；已有 `FEATURE_LAYOUT.json`、实际设计路径和实施记录优先。跨多个库、多个阶段的需求可按需增加 `delivery/database/README.md` 作为执行清单，由设计和实施记录链接；小需求直接使用已有文档。清单只登记步骤与链接，不复制另一份可编辑 SQL。

Agent 的既有迁移源继续使用 `apps/agent/migrations/`；后续 SQL 交付放 `apps/agent/db/main/sql/`，在该数据库 README 登记原源路径，不复制或搬迁历史。其他工具必须使用固定原生目录时，同样通过 README 登记唯一源。没有结构或受管数据变化的需求，标明“不涉及数据库变更”即可。

唯一源规则：

- 工具原生迁移源负责可执行的演进历史；ORM 模型描述应用预期结构，二者须验证一致。
- SQL-first 工具直接维护版本化 SQL；代码型工具从迁移源导出 SQL。不得人工分别维护两套相同变更。
- `bootstrap.sql` 与区间升级 SQL 是受管交付物，随相关迁移提交 Git，并通过再生成检查。临时输出、数据库 dump、真实数据与运行日志放 `work/` 或受控外部存储。
- 原生 SQL 本身已满足增量交付要求时，Feature 可直接引用原文件及校验值；不为凑齐路径制造副本。
- 需要复杂原始 SQL 时，固定在对应 revision 的资源中并校验；历史迁移不得读取持续变化的当前模型、通用业务函数或 `bootstrap.sql`。

## 4. 完整 SQL 与增量 SQL 的契约

### 4.1 完整初始化脚本

每个数据库维护一个稳定路径 `sql/bootstrap.sql`，表示当前代码基线支持的目标版本。生成方式优先为从空库版本重放完整迁移链；允许包含 CREATE / ALTER 及必需的数据转换。脚本作用于已创建且为空的自有 database / schema，不覆盖既有业务对象。

脚本必须建立工具版本记录，或随交付清单提供可验证的版本登记步骤；不能仅建表后随意 stamp 到最新。验证空库安装后，原生迁移工具应识别已达到目标版本，再次升级到同版本无新增操作。

若另外交付只含当前对象定义的 `schema.sql`，须从迁移到指定版本的临时数据库生成，登记与 bootstrap 相同的目标版本及生成方法；它只作结构参考，除非同时验收其初始化与版本登记流程。不能用 ORM `create_all` 代替迁移验收。

最新工作脚本可随新需求重新生成；已发布文件按 Git commit / 发布包固定并保留校验值，不覆盖旧交付。完整脚本不包含演示业务数据、真实账号、密码或无关 app 的对象；业务必需的参考数据可由迁移管理，演示 seed 使用独立入口。

### 4.2 需求增量脚本

涉及结构或受管数据变化的 Feature，为每个受影响数据库交付明确 `from → to` 的升级文件或原生 SQL 清单。文件名使用工具的稳定 revision；Feature 编号只用于追溯，不作为排序或版本号。多个 Feature 共享依赖时，区间可以包含前置需求，必须列清所需版本，不能只挑本需求文件绕过依赖。

执行前由受管入口核验目标库身份、起始 revision、源校验值和预期对象状态。不匹配时停止；不依赖全量 `IF EXISTS / IF NOT EXISTS` 隐藏漂移。同一目标只允许一个迁移执行者，使用工具或数据库锁，失败时记录实际版本和已完成步骤。裸 SQL 只有在上述前置检查、版本登记、锁与错误停止都受控时才可执行。

每份 SQL 文件头或其受管清单至少包含：owner / database-key、关联 Feature、源文件、from / to revision、数据库引擎与兼容版本、生成命令与工具版本、适用前提、事务边界、数据影响和恢复方式。交付清单登记源 commit（开发中可标明工作区未提交）与文件 SHA-256；校验值放清单，不让文件包含自身 hash。

SQL 生成能力按工具和迁移验证。依赖在线读取、Python / TS 数据处理或外部资源的步骤，必须标明不能离线执行的部分及顺序、可重试条件和验证入口。存在此类步骤时，不能把 SQL 文件宣称为完整升级包；SQL 加必要程序共同组成交付清单。

## 5. 历史、并行开发与恢复

- 已合入共享基线、已交付或已在共享环境执行的 revision 及其资源不可修改；修正新增迁移。仅尚未共享且仅在个人可丢弃数据库运行的迁移可整理，随后重建并重新验证。
- 每个迁移记录前置版本和关联 Feature。并行需求使用唯一 revision，合并时检查分支与依赖，按工具方式线性化或显式合并；发布时每个单位有明确目标，不留未解释的多个 head。
- 自动生成的迁移必须审查重命名、删除、类型转换、默认值、唯一约束、索引、数据回填与锁影响。不得把字段重命名当作删列重建而丢失数据。
- 有旧数据的新增非空列明确回填与约束生效顺序；长耗时回填按实际规模设计批次、检查点和重试。迁移本身按版本运行一次；可重试回填和 seed 另验幂等。
- 事务范围按数据库及 DDL 能力明确。不能放在同一事务的操作独立列步，说明中断后的继续或修复方式，不承诺整份脚本自动回滚。
- 每个变更选择实际可行的 downgrade、向前修复或备份恢复路径。删列后重新建列不能恢复原数据；不可逆操作明确前提、恢复材料和验证方法。
- 应用启动、模块导入、类型生成和 HTTP 契约导出不隐式执行迁移。迁移由独立受控任务执行，运行账号不持有 DDL 权限。

## 6. 跨应用需求与发布顺序

全局统一的是规范与执行清单；数据库分别拥有版本。一个需求修改 `web/main` 和 `agent/main` 时，分别生成和验证各自脚本，通过 API 契约定义依赖，不拼成假定跨实例原子提交的单个 SQL。

执行清单逐行记录：步骤、owner/database-key、from/to、脚本与 checksum、前置 API/版本、执行入口、成功条件、失败处理。所有依赖最终解析到具体版本，发布清单不使用漂移的 `head/latest`。先确保各库前置条件可满足，再按已验证的依赖顺序执行；后一库失败时保留前库实际结果，暂停新功能并按兼容窗口修复或恢复，不能声称全局已回滚。

支持滚动发布的破坏性变更按需求拆成扩展结构、发布兼容应用、回填/切换、确认旧消费者退出、收缩结构。简单加表无需套用完整分阶段机制；跨库步骤也不为迁移引入新的常驻协调服务。

## 7. SDD 各阶段交付与完成条件

本节适用于 simple / standard、项目覆盖模板和直接小任务。各阶段遵循项目规则；没有单独测试计划时，把必要验证放入设计任务和实施记录，不能省略验证。

| 阶段 / Skill                                | 数据库相关交付                                                                    | 完成条件                                                              |
| ------------------------------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 需求 / `my-create-feature`、`my-create-prd` | 标记数据变化、所属 app / 逻辑库、旧数据与兼容约束、可判定 AC                      | 不明确的 owner 或数据保留要求先澄清                                   |
| 设计 / `my-create-design`                   | 变更对象、源路径、版本依赖、完整/增量 SQL 交付、在线步骤、发布/恢复顺序及验证任务 | 每张表有 owner；跨 app 引用和迁移工具已确定；拟新增文件与现有文件分开 |
| 设计评审 / `my-review-design`               | 核对职责、跨库依赖、数据安全、兼容窗口、恢复与最小实现                            | 无影响实施的未解决设计问题；大规模或不可逆风险有依据                  |
| 实现 / `my-implement-code`                  | 迁移源、模型同步、两类 SQL 或原生 SQL 清单、README 与真实命令、Feature 关联记录   | 交付可复现；无手改派生物、历史漂移与虚构工具入口                      |
| 代码评审 / `my-review-code`                 | 检查实际 diff、版本链、数据处理、权限、错误/锁/重试和上下游兼容                   | 自动生成的迁移已审查；实现与设计一致                                  |
| 测试 / `my-create-test-plan` 或实施验证     | 复用既有覆盖，补齐下列矩阵与当前执行证据                                          | 必需项通过；未执行、受阻和跳过分别报告                                |
| 结项 / 发布                                 | 固定源版本、各库 from/to、交付 checksum、执行清单与恢复材料                       | 所有本次承诺条件均有当前通过证据，运行环境版本可核对                  |

### 必须覆盖的验证

1. **空库安装**：原生迁移链和完整 SQL 分别在隔离的目标引擎数据库执行，结构及版本记录一致。
2. **旧库升级**：从声明的起始版本装载有代表性的旧数据，分别验证原生迁移与增量交付；数据、约束、索引和目标版本符合预期。无需新建重复测试，已有充分覆盖可引用。
3. **执行控制**：错误起始版本或目标拒绝；达到目标后重跑受管入口无重复变更；实际涉及非事务或在线步骤时验证失败恢复与重试。
4. **访问与业务**：运行账号仅操作自有对象；跨 app 走契约；相关 CRUD / 推理路径、当前权限及兼容行为通过。
5. **生成一致性**：重新生成受管 SQL 无差异，模型与迁移目标一致；固定版本、排序和换行等生成因素，去除无意义时间戳与环境噪声。
6. **恢复**：对承诺的 downgrade / 前向修复 / 恢复方案做相应演练；破坏性变更验证数据恢复，不只检查表能重建。

使用真实目标数据库验证引擎特性，SQLite 不能代替 PostgreSQL 迁移验收。现有 Agent 链路继续执行 `pnpm db:migrate`、重复 `pnpm db:seed` 和 `pnpm smoke`；新 app 使用其实际登记的入口。生成、迁移和真实数据库验证按项目任务规则隔离环境与缓存；SQL 差异检查只有在完全确定性且缓存输入完整时才可缓存。

## 8. 现状、例外与接入顺序

本次交付为项目规范与架构职责同步，未新增数据库、ORM、迁移工具、SQL 导出命令或自动 CI 门禁。Web / Memory 的首次持久化 Feature 必须同时交付本规范要求的入口与验证；下一次修改 Agent 应用库时补齐其 SQL 生成与验收能力。工具尚未实现时明确列为实施任务，不能仅凭规范文件报告自动检查已生效。

998 零售数据采用“冻结业务包 → 新候选库 / schema → 验证 → 活动清单切换”，沿用 [data-seeding.md](data-seeding.md) 的专用账号、版本、摘要与回切。其现有 DDL 唯一源是 [business-schema.sql](../mai-specs/998-business-data-seeding-tool/design/business-schema.sql)，迁移入口会读取该源；回放必须固定整套源版本与摘要。这是现有数据发布机制的登记，不可复制为应用库历史迁移读取最新 SQL 的做法。原位升级既有零售库须单独设计并满足本规范，不能把重建候选当作原位迁移。

目标系统数据设计仍按 Feature 切片落地，不一次创建全部目标表。工程规范更新不改变 PRD 业务范围、功能验收状态或现有演示数据库。

## 9. 技术依据

- [Alembic 离线 SQL](https://alembic.sqlalchemy.org/en/latest/offline.html)：支持固定版本区间导出；依赖在线读取的迁移需另外处理。
- [Alembic 自动生成限制](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)：候选迁移须审查，尤其是重命名与数据变化。

以上为工具能力依据；目录、owner、SDD 门槛与交付策略由本项目确定。Web 迁移工具在首个数据库需求中选定，不强制 Node 服务依赖 Python 迁移环境。
