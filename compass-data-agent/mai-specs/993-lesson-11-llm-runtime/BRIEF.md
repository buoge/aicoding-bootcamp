## 一句话描述

为 Compass 建立统一的 LLM Runtime，贯通模型 Provider 的持久化管理、界面能力测试、分析 Chat 主模型选择与真实模型调用，完成第 11 课的架构选型和工程落地。

## 背景

本需求服务于《企业级Agent工程架构实战营》正式课第 11 课，承接 Compass 已交付的工程基座与 Web 管理框架。当前模型执行尚未接入，需要建立可供后续 Agent 能力复用的模型调用入口，并让管理员能够配置、测试和维护模型接入。

2026-11-03 用户进一步明确：产品侧围绕现有“管理与治理 → Agent 与能力 → 模型路由”模块提供轻量模型接入管理与测试，并让用户在分析 Chat 中手动选择主模型；技术侧完成整个 DataAgent 的 LLM Runtime 分层架构设计，贯通 Web、核心 Agent API 与 Runtime 的调用流程。

第 11 课页级大纲当前处于评审中。本 Feature 以用户明确的工程需求为范围依据，并与课程中的模型执行边界、统一契约、能力差异和分层设计相衔接。

## 需求概览

### 产品层面

#### 1. 模型 Provider 管理与持久化

- 平台管理员在“管理与治理 → Agent 与能力 → 模型路由”模块中添加、查看和维护可接入的模型 Provider，配置持久化到数据库。模型由平台统一管理并向各租户提供，平台管理员可从平台上下文进入管理模块。
- 模型接入类型覆盖 LLM、决策模型等。本需求中的 Provider 管理面向一项可供调用和选择的模型接入配置。
- 核心管理字段为模型名称、别称、Base URL、API Key，以及是否允许在分析 Chat 中展示；支持维护接入状态。
- 保持轻量管理范围，不建设 LiteLLM Proxy 式的复杂模型管理平台。API Key 由服务端安全保存和使用，界面按权限维护并脱敏展示。

#### 2. 分析 Chat 手动选择主模型

- 分析 Chat 本期只开放 deepseek v4 pro、deepseek v4.1 flash；平台管理员控制这两款 LLM 的 Provider 是否展示，租户用户按权限使用。阿里云 decision-model-preview 仅在管理端配置和测试。
- 用户在分析 Chat 框中手动选择对应的模型 Provider 作为主模型；该选择应传递到 Agent API 和 LLM Runtime，并用于实际调用。
- 模型列表和调用遵守配置状态及用户权限；仅供后台测试的配置可保留在管理端。

#### 3. 界面化模型能力测试

- 管理员可直接在界面中测试已接入模型，配置测试输入和调用参数，查看调用结果及必要的状态、用量、耗时和错误信息。
- 测试入口覆盖已接入 LLM 实际支持的功能，至少包括同步（非流式）调用、流式输出、工具调用、Thinking 开关及思考强度、结构化输出。
- 工具调用测试应能配置工具声明并检查模型返回的调用信息；决策模型按自身输入和结果语义提供测试能力。
- 界面明确展示各模型可用的能力和参数限制，反馈不支持的能力或参数组合。

#### 4. LiteLLM 模型清单选择

- 添加 Provider 时，支持从 LiteLLM 支持的模型清单中下拉选择模型。
- 选定模型后，可维护对应的模型名称、别称、Base URL 和 API Key，完成接入配置与测试。
- 模型目录的获取、更新与具体映射方式在后续设计中确定。

### 技术层面

#### 1. LLM Runtime 整体分层架构与第 11 课落地

- 完成整个 DataAgent 的 LLM Runtime 技术架构选型与分层架构设计，明确模型执行边界、统一调用契约、模型配置与能力表达、Provider 适配、调用执行及基础观测的职责。
- 参考 [DataAgent LLM Runtime 架构材料](context/DataAgent_LLM_Runtime_Architecture_v1.0.md) 中的进程内薄层、统一契约及生成模型与决策模型适配思路；具体实现方案在后续技术设计中确定。
- 完成第 11 课所需的统一执行入口、多模型接入、能力差异处理与最小调用链路，为后续课程扩展保留清晰边界。

#### 2. Web、Agent API 与 Runtime 流程贯通

- 贯通“Web 管理界面 → 核心 Agent API → 模型配置持久化”，使已保存配置可用于后续测试和模型调用。
- 贯通“界面能力测试 → Agent API → LLM Runtime → 模型 Provider → 结果展示”，支持流式与非流式调用的完整返回流程。
- 贯通“分析 Chat 选择主模型 → Agent API → LLM Runtime → 所选 Provider”，确保用户选择影响实际执行。
- Web 复用现有身份、权限与审计能力；Agent 负责 Runtime、模型运行配置与调用状态，各应用通过 HTTP 契约衔接。

#### 3. 本课配套交付

- 三个指定模型分别完成真实接入、调用调通和适用能力测试。
- 补齐调用所需的能力检查、错误反馈、基本超时与取消处理，以及定位问题所需的调用记录。
- 完成模型配置的数据库持久化、必要迁移、凭据保护、管理权限和 Chat 可见性控制，保留既有账号、租户、演示数据及历史记录。
- 提供本课可演示的操作流程和必要的集成验证，覆盖新增 Provider、保存配置、能力测试、Chat 选模与实际调用。

### 本轮范围边界

- 当前已形成需求概览、PRD 与技术方案，Feature 保持 `draft`；技术方案按 MVP 设计 Agent 内薄 Runtime、三模型适配、平台管理与单次调用链路，实施尚未开始。
- 模型接入采用轻量配置与用户手动选择。复杂自动路由、自动降级、全局预算配额、完整 Trace/Replay 与发布治理继续与第 12–14 课衔接。
- Agent Loop、业务工具实际执行、SQL 执行、持久任务调度、Memory 与 Sandbox 由对应需求承接；本课完成模型能力调用及所需的产品入口贯通。
- 持久化遵循项目数据库规范：模型运行配置归 Agent/main，Web/main 复用身份、权限和审计。设计阶段登记具体数据变化、迁移版本、SQL 交付与恢复安排。

## 关键决策

2026-11-02 用户明确本需求共支持以下三个模型的接入：

1. **deepseek v4 pro**：旗舰模型。
2. **deepseek v4.1 flash**。
3. **decision-model-preview**：阿里云决策模型。

三个模型均纳入统一 Runtime、真实调用调通及相应基础管理范围；决策模型通过管理端测试入口调用，Chat 仅承接两款 DeepSeek LLM。后续设计核实各模型的 API 标识、接入端点、协议、凭据配置与能力支持，并分别明确验收条件。

2026-11-03 用户明确产品入口、数据库持久化、Chat 主模型选择、界面能力测试及 LiteLLM 模型清单下拉选择。以上需求覆盖此前尚待明确的管理与测试范围。

2026-11-03 PRD 编写期间，用户确认采用“平台统一管理，向各租户提供模型”。模型配置与凭据由平台管理员维护，租户用户使用平台开放的模型。

2026-11-03 用户确认“本期仅在管理端测试决策模型，Chat 只开放两款 LLM”。决策模型的 Chat 展示保持关闭，不建设决策 Chat 表单或自动转换；管理端的配置与独立测试继续交付。

架构材料作为技术参考保留原文。其“决策模型待定”及静态文件配置描述，在本需求中按已指定的阿里云 `decision-model-preview` 和数据库持久化管理要求落实。Runtime 库与宿主应用的职责在后续设计中衔接。
