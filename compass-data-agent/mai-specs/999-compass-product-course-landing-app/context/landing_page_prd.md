Part 1：电商 DataAgent 产品需求讲解
目标：让学员知道最终产品服务谁、解决什么问题、怎样完成业务闭环。
二级大纲／页面标题 本页主要讲什么
1.1 我们最终要做出一个什么产品？ 原型界面截图+一句话介绍。以及系统服务的客户
1.2 谁会使用它，分别希望解决什么问题？ 列出系统相关的角色及关系图，以及每种角色需要用到的场景及系统对应的功能清单
1.3 产品架构：用户会在哪些地方完成工作？ 展示完整的产品架构地图
1.4 功能全景：这个产品由哪些能力组成？ 将现有功能域归入业务分析、任务执行、数据与能力管理、质量与治理等分组；标记课程重点建设、脚手架提供和扩展选学部分。
1.5 业务逻辑：一个经营问题如何走到可验证的结果？ 串起问题澄清、口径确认、分析计划、数据查询、证据校验、报告建议、动作草案、审批执行、效果追踪；讲清信息不足、分析失败、审批拒绝等主要分支。
1.6 项目范围：做到什么程度，算完成这个产品？ 明确必做场景、选做场景和范围边界；用可演示、可验证的业务结果定义结课验收，避免学员把“界面能聊天”当作完成标准。

这一部分建议始终围绕同一个主案例展开，再用库存风险、退款异常、广告预算调整补充不同类型的需求。
Part 2：电商 DataAgent 技术需求与架构讲解
目标：把产品需求翻译成工程全景，让学员理解后续每项技术工作的用途。
二级大纲／页面标题 本页主要讲什么
2.1 从产品需求推导技术要求 将可信分析、长任务、审批执行、可恢复、可追踪、成本控制、权限隔离等业务要求，映射到具体工程要求。
2.2 系统总体架构：各部分怎样协作？ 展示前端与 BFF、业务服务、任务调度、Agent Runtime、工具与执行环境、数据存储，以及安全、观测、评估等贯穿能力。区分逻辑模块与实际部署进程。
2.3 一次分析请求，怎样穿过整个系统？ 用简化时序图讲清从用户提交问题，到创建任务、调用模型与工具、保存证据、生成报告、反馈进度的全过程；标出失败与恢复位置。
2.4 核心模块：各自负责什么，怎样连接？ 介绍 LLM Runtime、Agent Runtime、Context、Tool／Skill／Action、Memory、EvalOps 的职责、输入输出与依赖关系，建立后续课程的模块地图。
2.5 技术选型：我们用什么，以及为什么这样选？ 给出前后端、数据库、模型接入、任务调度、分析执行、测试与部署的选型表。每项只讲承担的职责、选择理由和适用阶段。
2.6 架构如何演进：启动版本怎样走向完整系统？ 展示从基础工程、模型接入、可靠执行，到上下文与能力、记忆、评估发布的演进过程；标记本课确定的基线和后续课程需要完成的设计决策。

架构选型方法、框架横向比较、复杂分布式细节，在这一部分适当收束。重点是让学员看懂“为什么项目需要这些组成部分”。
Part 3：项目脚手架介绍——大家从同一起跑线出发
目标：明确老师交付什么，以及学员如何确认自己已经具备开工条件。
二级大纲／页面标题 本页主要讲什么
3.1 项目启动包：老师已经为你准备了什么？ 清点代码、界面与交互参考、接口契约、配置示例、数据、启动工具、基础测试和说明文档；标明已实现、教学桩、待开发部分。
3.2 代码地图：后续开发分别发生在哪里？ 用目录与架构对应图介绍前端、后端、共享契约、数据库迁移、测试和各能力模块的扩展位置，让学员知道后续课程要打开哪些地方。
3.3 数据准备：我们拿什么数据做分析和验证？ 介绍订单、商品、库存、会员、投放、售后等目标业务数据域，以及指标口径、场景样本和异常样本；明确当前启动包实际包含的数据范围。
3.4 软件与账号要求：开始前需要准备什么？ 列出运行环境、开发工具、容器环境、模型账号与配置、网络要求和资源要求；说明版本锁定、不同操作系统的差异及凭据管理方式。
3.5 启动验收：怎样证明你已经准备好了？ 演示安装、配置、初始化数据、启动服务和健康检查；通过一条前端到数据库的完整链路确认基线可用，并给出常见问题的定位入口。

这里有一个需要保留的现实边界：仓库目前已有 Compass 的 M0 工程脚手架，基础前后端与数据库链路已经打通。完整 Agent、审批、记忆和评估等能力属于后续建设内容。PPT 应分别标注当前实际交付和计划提供的教学资源，数据也采用同样口径。
Part 4：课程任务拆解——随着课程推进完成项目拼图
目标：把后续课程变成一张可执行、可验收的项目任务地图。
这是本课最值得做扎实的部分，建议保留六张相互关联的清单。
二级大纲／页面标题 本页主要讲什么
4.1 项目路线图：每个阶段会增加什么能力？ 对应第 11–40 课，展示模型、Agent、上下文、工具与 Skill、记忆、评估六条主线；每个阶段标出入口条件、主要增量和可演示结果，第 41 课完成综合验收。
4.2 模块开发清单：我们要完成哪些工程模块？ 按能力主线列模块和子模块，说明老师提供的基础、学员需要实现的内容、涉及课次、依赖和完成标准。明确“产品功能域”和“工程开发模块”的统计口径。
4.3 Tool、Skill 与 MCP 清单：要开发哪些具体能力？ 逐项列出指标查询、业务查询、Python 分析、报告生成、广告查询与预算调整等能力，以及经营异常诊断 Skill、MCP 服务；确定必做与选做数量，说明复用关系和验收方法。
4.4 评估建设清单：要定义哪些标准、准备哪些案例？ 从结果正确性、执行过程、系统表现三个维度，盘点质量标准、硬性门槛、评分项、测试案例、评分器和回归集；分别统计，避免把不同对象混成一个数量。
4.5 架构设计清单：课程中要完成哪些设计决策？ 盘点总体架构、模型接入与治理、Agent 执行、部署拓扑、上下文、能力接入、记忆和评估发布等设计任务；每项明确要回答的问题、设计产物和对应课次。
4.6 最终交付清单：所有拼图完成后，我们拿什么验收？ 汇总代码、工具与 Skill、架构记录、数据与评估集、测试报告、运行证据和演示材料；通过正常业务、故障恢复、能力演进三类演示完成综合验收。

建议所有清单使用同一组字段：
编号｜任务名称｜对应课次｜老师提供什么｜学员完成什么｜前置依赖｜验收证据｜必做／选做
数量直接从这些清单汇总，最终形成一页醒目的“项目总账”：开发多少模块、多少工具、多少 Skill，完成多少项架构设计，定义多少条评估标准。
目前文档已有 16 个产品功能域和六条后续能力主线，但具体开发任务存在复用与拆分关系。工具、Skill、评估条目和架构设计的最终数量，建议在下一轮逐课核对后确定。
Part 5：后续课程注意事项——怎样学、怎样做、怎样交付
目标：让学员掌握固定的学习节奏和作业规则。
二级大纲／页面标题 本页主要讲什么
5.1 后续每节课怎么讲：从项目问题走到可验证的改进 建议统一授课结构：当前问题 → 设计判断 → 老师演示 → 关键实现 → 验证结果 → 本课任务。每次开课说明当前项目状态，结束时展示新增能力。
5.2 每节课怎么学：课前准备、课中理解、课后实现 说明预习资料、基线检查、课中关注点和课后开发步骤；给出基础必做与进阶选做路径，以及卡住后的处理方式。
5.3 作业怎么安排：随堂任务、阶段作业、结课项目 区分小步练习、阶段综合交付和最终项目；明确哪些任务累积到主项目，哪些用于验证单项能力，并说明阶段检查点和预计投入。
5.4 作业怎么提交和评价：交代码，也交验证证据 统一提交内容：代码版本、运行说明、测试或评估结果、关键设计说明、演示证据；说明评分规则、反馈方式和补交机制。
5.5 协作与开发约定：如何持续跟上项目进度？ 约定版本同步、问题反馈模板、AI 辅助开发要求、数据与密钥管理、资源成本控制；最后布置第 10 课启动任务：跑通基线、完成环境检查、记录问题、阅读下一阶段任务。
