## 1. 执行摘要

Compass 是面向品牌商家与零售企业的多租户经营分析与决策协作平台，DataAgent 是其产品类别与历史设计称呼。普通用户首页采用 ChatGPT 式会话与分析输入：用户先表达经营意图，系统再按当前租户、角色、指标语义和可用能力生成可审查的任务契约，把“提出经营问题”到“形成可核验结论并受控执行行动”的过程组织为一个可追踪、可恢复、可评测的 Agent Run。

主 Agent 根据目标、口径和可用数据选择分析路径，在既有授权与预算内调用工具、技能、固定流程和子 Agent；它根据中间结果调整计划，校验证据并交付版本化产物。查询、图表、文件清洗、对账、诊断、预测、实验和因果评估各自遵循对应的方法与完成标准。执行外发、额外开支和业务写入前，系统检查具体授权；待授权动作先形成可审阅草稿。

DataAgent 同时承担课程的统一工程载体：产品业务面保持稳定，底层能力从模块化单体逐步演进为支持多模型、多租户、长任务、分布式执行、上下文治理、能力治理、记忆治理和 EvalOps 的企业级系统。

### 1.1 本轮有效依据与交付边界

2026-10-20 用户明确要求一个 Web 系统，以可组合岗位角色与细粒度权限决定每位用户看到的模块；普通用户使用 AI Native Data Agent，部门管理者与管理员获得各自授权的治理能力。本轮依据为 [行业设定](../context/product_definition_industry.md)、[系统需求](../context/product_definition_system2.md) 与本次用户说明。源材料中的规模、品牌和经营情节仍为课程仿真设定。

本轮交付完整产品规格、设计体系与 HTML 原型。原型使用合成数据演示 12 类分析任务和全部功能域；当前 Compass 工程仍为 M0 脚手架。原型的交互覆盖、产品规划与生产实现分别验收。课程 Landing Page 的具体主题、页面与发布范围仍在 Feature 999 中等待独立范围定义。

## 2. 产品机会

### 2.1 目标客户面临的问题

零售经营分析通常横跨订单、商品、库存、会员、广告和售后系统，真实决策仍存在四类断点：

1. **数据到口径的断点**：字段可查不等于指标可信；同名指标常有时间、币种、退款和渠道口径差异。
2. **口径到结论的断点**：分析师需要手工拼接 SQL、表格和脚本，结论难以追溯到具体证据。
3. **结论到行动的断点**：报告与工单、预算和运营系统分离，建议无法形成可验证闭环。
4. **自动化到责任的断点**：通用 Copilot 可以生成答案，却难以回答使用了什么权限、何时应该停止、失败后怎样恢复、谁批准了真实操作。

### 2.2 机会陈述

如果企业能把经营分析建模为“有目标、有状态、有证据、有边界、有审批、有反馈”的任务系统，就可以在不牺牲数据安全与业务责任的前提下，缩短从发现异常到采取行动的周期，并把每次分析沉淀为可复用、可评测的组织能力。

## 3. 产品愿景与使命

**愿景**：让每一个重要经营判断，都能被数据证明、被组织理解、被安全执行。

**使命**：为零售企业提供可信、可控、可持续演进的 Agent 分析与决策工作台，把跨系统经营问题转化为可核验的证据链和可治理的行动闭环。

### 3.1 一句话定位

DataAgent 是一个面向多租户零售企业的 Agentic Analytics SaaS：它自主完成复杂经营分析，并让每个结论可追溯、每个高风险行动可审批、每次系统演进可评测。

### 3.2 价值主张

| 价值 | 对业务用户 | 对企业管理员 | 对研发与平台团队 |
|---|---|---|---|
| 更快 | 从问题到初步结论由天级缩短到小时/分钟级 | 统一配置与批量治理 | 复用 Runtime 与能力平台，减少烟囱式 Agent |
| 更可信 | 结论附指标口径、数据新鲜度、SQL/Artifact 和证据引用 | 全链路权限与审计 | Trace、Replay、Eval 使问题可定位、变更可回归 |
| 更可控 | 关键步骤可暂停、补充信息和接管 | 风险策略、审批链、预算和配额可配置 | 自主性预算、幂等、Checkpoint 和回滚控制故障半径 |
| 更有闭环 | 建议可转工单草稿或外部平台草稿，并跟踪确认状态 | 统一查看行动与结果 | 外部交接回执把模型提议与最终业务提交解耦 |

## 4. 目标市场与产品形态

### 4.1 理想客户画像（ICP）

- 拥有至少两个线上/线下销售渠道，经营数据分散在多个系统的品牌商家；
- 具备数据仓库、BI 或分析团队，希望提升分析效率但不能放松权限与审计的中大型零售企业；
- 运营、商品、供应链和广告团队之间存在高频跨域分析协作；
- 愿意从只读分析开始，逐步引入受控业务行动。

### 4.2 核心用户角色

| 角色 | 核心任务 | 核心价值 |
|---|---|---|
| 经营负责人 | 查看全局趋势、诊断关键异常、批准高风险动作 | 快速获得可信结论并保留决策权 |
| 业务分析师 | 发起复杂分析、核验过程、下钻证据、复用报告 | 减少机械查询，把精力转向判断 |
| 运营/商品/广告经理 | 获取领域建议、创建工单、调整策略、追踪效果 | 缩短分析到执行的链路 |
| 审批人 | 评估影响、检查证据与差异、批准或驳回 | 在明确上下文中承担业务责任 |
| 租户管理员 | 配置成员、角色、数据接入、指标口径、用量和审计 | 让经营分析符合企业数据与权限政策 |
| 数据治理人员 | 维护指标口径、血缘、质量、新鲜度和访问策略 | 防止“查得到但解释错” |
| 平台运维/审计人员 | 查看 Run、Trace、成本、故障、版本和审计事件 | 保障系统可运营、可追责、可演进 |

### 4.3 一个 Web 系统与可配置工作区

Compass 使用同一 Web 入口、同一认证主体、统一导航框架、任务模型与审计记录。经营分析和管理控制台是同一系统的视图。用户可以同时担任区域经理、分析师和审批人，界面展示由授权能力集合决定；岗位名称仅作为可调整的权限模板。

- **五个业务一级入口**：分析、报告空间、插件、定时任务、看板。分析默认进入居中问题输入与聚合看板案例的首页；二级栏保存全部授权会话，提供新建、标题区图标打开的全文搜索弹窗、主题分组或时间排序。报告和看板独立浏览，插件集中承载 Skill、Prompt、Agent、模板与数据集。
- **完整会话**：每次新建使用独立 taskId；中间持续展示完整用户/Agent 消息、可展开分析摘要与工具记录、输出、行内产物、消息操作、人工授权及底部输入，可在原上下文继续聊天。相同分析模板可以创建多条互相隔离的会话。分析摘要服务过程核验，模型私密原始思维链不属于交付对象。
- **会话管理**：侧栏以单行标题配合运行、待授权和未读标记显示状态；hover/focus 可改名或删除。删除可撤销并独立保留报告空间产物；全文搜索支持键盘选择、打开与关闭。
- **部门与工作区管理**：在授权部门、区域、渠道或工作区内管理成员、报告复核、团队资产、周期任务与预算；没有授权时不能修改组织级口径、模型或连接。
- **管理与治理**：作为获权用户的一级入口，二级按权限呈现控制总览、数据与语义、Agent 与能力、运行与调度、质量与发布、安全与审计、记忆与产物、组织设置，保留十个管理领域的职责。
- **平台运营视图**：跨租户运行元数据、容量、依赖与平台发布。平台角色默认不获得企业业务内容读取权。

左侧一级采用窄图标栏，悬停/聚焦显示标题；二级固定展开时占据布局空间，收起后可通过悬停浮层或键盘/触屏等价操作访问。场景库和待我决定留在分析二级，设计指南位于导航底部。

本轮原型的报告空间、插件和看板暂共用 assets 模块授权，动作权限与数据范围独立；产品规划保留三者独立授权的后续实现能力。

案例说明、自动播放/暂停、十二场景与细分状态选择统一放在右侧临时“演示面板”，仅服务原型评审；窄屏以默认收起的右侧抽屉承载。自动演示允许模拟本地人工授权并明确标记；正式会话中的授权卡继续遵循责任人、对象版本与权限契约。迁入生产时移除演示工具，保留完整会话体验。

租户管理员可以向数据维护者、Agent 维护者、运行维护者和审计员委派租户范围的能力。平台 Provider 注册与跨租户策略保持独立权限。旧版将全部模型/Skill 配置固定归平台的限制由这一能力授权规则取代。

移动端保障会话、任务进度、产物阅读与人工决定；复杂语义编辑、评测配置和深度运行诊断提供摘要与桌面提示。

### 4.4 主示例企业与行业边界

主示例为虚构的**行野运动集团**，首期经营中国市场，包含大众运动、专业跑步和户外三个品牌，7 个经营大区、约 80 个城市、240 家门店、8 个配送中心、36 个月经营历史；完整数据目标约 8,000 个 SPU、60,000 个 SKU。规模是仿真配置目标，原型只使用可解释的小样本。

一级品类为运动鞋、运动服装、露营与徒步、骑行、健身、球拍与球具、水上与冰雪、运动配件与耗材。品牌、主品类、运动标签分别建模；SKU 承载颜色、尺码与规格。渠道包括天猫、京东、抖音、自有 App/商城、小程序、标准门店与奥莱。

一个租户对应一家独立企业。品牌、区域、渠道和门店是租户内经营维度。另设两家小型合成企业验证租户隔离。营销来源、下单渠道、需求区域、销售归属、履约地点与退货地点分别保存，跨城退货保留原销售归属。

重点岗位包括 CEO、市场总监、电商负责人、商品/供应链负责人、区域经理、BA/分析师和数据平台管理员。所有岗位的事实问答、看板与周报共享已发布的指标语义。

## 5. 核心产品原则

### P0. 意图优先，界面由任务生成

普通用户登录后的第一交互对象是问题输入框、推荐问题和任务模板；看板、报告与数据对象既可作为输入上下文，也可由 Agent 分析结果生成或更新。系统从用户意图进入任务契约，并保留用户在当前页面选择的上下文。

### P1. 先口径，后数据

在访问数据前明确指标定义、时间范围、粒度、币种和权限。关键语义缺失时必须澄清或停止，不允许模型猜测。

### P2. 证据是独立产品对象

每个关键 Claim 必须关联 Evidence；证据包含来源、查询/计算方式、版本、新鲜度、质量状态和访问权限。用户可以从报告下钻到证据和运行轨迹。

### P3. 模型提议，系统校验，人对高风险行动负责

M0 只允许只读分析，并为高风险调整生成不可变草稿；草稿经业务负责人确认后交给外部系统，由外部责任人最终发布。直接业务写入、自动补偿与受控执行仅作为 M3 以后候选能力，不能在首版原型中承诺。

### P4. 长任务是有状态业务流程

会话可以产生多个任务，每个任务可以包含多次运行。Run 必须有状态机、Checkpoint、预算、停止条件、超时、取消、恢复和失败解释。

### P5. 多租户是端到端不变量

Tenant、Principal 与授权上下文必须贯穿入口、Context、Query、Queue、Store、Worker、Sandbox、Artifact、Memory、Action 和 Telemetry；不能只依靠前端租户选择器或 Prompt 字段。

### P6. 权威数据、运行状态和长期记忆严格分层

Memory 只保存经策略允许且可纠正/删除的信息，不复制实时经营事实、指标权威定义或历史权限。每次任务重新验证当前数据与授权。

### P7. 每次变更都必须可比较、可回归、可回滚

模型、Prompt、Context Policy、Tool、Skill、Memory Policy 与代码共同构成行为版本。候选版本必须通过可复现 Fixture、硬安全门槛和灰度策略。

### P8. 渐进增强而非“大爆炸平台化”

先以模块化单体建立业务基线，再根据明确的可靠性、隔离和规模需求拆分 Runtime 与治理服务；产品契约保持稳定，部署形态允许演进。

### P9. 课程能力不自动成为产品表面

课程需要承载的 Runtime、Memory、Eval、Tool 与治理机制，不因其理论重要性就获得一个页面或一级入口。只有当某类用户存在独立目标、明确责任和可验证使用路径时，才形成产品表面；其余能力留在系统契约、对象详情、内部平台或后续里程碑。原型中的可见控件必须有可观察结果，不能用死按钮暗示尚未定义的功能已经完成。

## 6. 核心任务与端到端闭环

```mermaid
flowchart LR
    A["经营问题与目标"] --> B["任务澄清与指标口径确认"]
    B --> C["自主分析计划"]
    C --> D["数据查询与 Python 分析"]
    D --> E["证据验证与原因排序"]
    E --> F["报告与行动建议"]
    F --> G{"行动风险等级"}
    G -->|只读/低风险| H["自动完成或创建草稿"]
    G -->|中高风险| I["人工审批"]
    I --> J["受控执行与验真"]
    H --> K["效果跟踪"]
    J --> K
    K --> L["反馈、评测与受控演进"]
```

### 6.1 代表性任务

1. 诊断“华东区本周 GMV 同比下降 12%”的原因，并给出有证据的优先行动。
2. 分析退款率异常，区分商品质量、物流延迟、营销人群和渠道政策因素。
3. 识别未来 14 天的缺货风险，提出补货建议并创建待审批工单。
4. 评估广告活动边际回报，生成预算调整草稿，经人工确认后发送到外部广告平台等待最终确认。
5. 每周一自动生成经营周报，监测异常并持续跟踪上一周期行动效果。

### 6.2 十二类任务与持续工作方式

| 类型 | 目标与主要产物 |
|---|---|
| S01 快速问数 | 同口径答案卡、结果表与查询引用 |
| S02 交互探索 | 可追踪筛选、下钻分支与交互图表 |
| S03 文件清洗与跨源关联 | 派生数据集、转换代码、匹配和质量报告 |
| S04 对账与质量调查 | 差异桥接表、对账报告与修复提案 |
| S05 异动诊断 | 贡献表、假设与反证、诊断报告 |
| S06 深度专题 | 问题树、多分支综合、可复算分析包 |
| S07 预测与情景模拟 | 基线、回测、误差、区间与情景参数 |
| S08 随机实验评估 | 分流质量、效应区间、护栏和决策标准 |
| S09 观察性因果评估 | 识别前提、诊断、敏感性与结论限制 |
| S10 周期报告 | 固定定义、每期实例、数据就绪和投递回执 |
| S11 主动监控 | 规则、异常事件、去重冷却、调查和恢复记录 |
| S12 看板与分析应用 | 参数、图表绑定、发布版本和访问控制 |

过程界面展示真实可观察的目标、计划、方法摘要、工具动作、假设证据与修订，避免把模型内部思维链作为交付目标。只在实质歧义、重要资源取舍或新增授权出现时请求人工介入。业务澄清、计划对齐、执行授权、结果复核与发布授权分别记录。

### 6.3 数据与指标策略

采用统一、可控的 Python 规则生成器连接商品、订单/POS、仓储履约、售后、会员、营销、自有渠道行为和经营计划；公开数据集仅作模型参考或独立测试，禁止用随机身份关联制造跨源漏斗。

生成过程保留业务发生时间和入库时间；金额、支付、退款和库存必须能够对账。订单行引用成本历史；库存平衡保留缺货零记录；同一 SPU 的汇总库存不能代替 SKU 与地点的可售库存。跨渠道会员身份仅在有依据时关联。

支付 GMV、净销售额、毛利、渠道贡献分别定义。报告必须显示退款成熟窗口、时间口径、截止时间和版本。观察性归因与活动增量分别表述，统计分析不承担法定财务结论。

每个经营情节保存发生时间、影响范围、变化参数、业务证据、参考查询与预期结论限制。重点情节包括大促贡献下降、热门尺码缺货、新店掩盖同店下滑、售后成熟后活动回报下修、数据晚到与业务下降区分、补货延迟。指标与规模验收详见 [PRD 第 15 节](PRD.md#15-行业经营模型与数据验收)。

## 8. 产品范围

### 8.1 首个可教学产品基线（M0）

M0 必须形成一个完整但受限的垂直切片：

- 以行野运动集团为主示例，补充两个小型租户的隔离样例；预置商品、订单、库存、会员、营销、售后、履约与目标数据；
- AI Native 首页：问题输入、角色化推荐问题、待处理事项与最近上下文；
- 唯一纵切为“提出问题 → 确认范围 → 后台分析 → 查看数据依据 → 提交报告复核”；
- 分析二级承载全部会话与工作记录，报告空间、插件、定时任务和看板使用独立业务入口；复核与调整草稿仍以具体任务对象进入待我决定；
- 两个团队预置经营看板；用户可把一次分析保存为持续监控草稿，首版不建设通用拖拽式看板编辑器；
- 同一 Web 内多租户登录与可组合岗位/管理权限演示，支持成员、角色、数据范围与可见能力预览；
- 以支付 GMV、净销售额、毛利、渠道贡献为核心，并提供订单数、客单价、转化率、退款率和库存周转；
- 一个“广告预算调整草稿”的确认与外部交接模拟；首版不宣称直接写入生产广告平台，也不按短期 ROAS 自动回滚；
- Run Timeline、Artifact、基础 Trace 和 Seed Eval Set；
- 模块化单体实现，但领域契约不绑定具体模型或框架。

### 8.2 本轮完整原型范围

本轮 HTML 原型覆盖 S01–S12 的主要组件组合和状态、108 项系统功能的可发现入口或详情、完整管理员控制面与权限配置预览。示例查询、Agent 运行、上传处理、发布、外部集成、模型切换与运维动作使用本地模拟；以明确标识和反馈维护真实能力边界。生产能力仍按下一节逐步实施，不因原型展示而提前宣布通过生产验收。

### 8.3 课程完成态（M5）

- 多租户、RBAC/ABAC、数据与资源隔离；
- 角色化经营分析、企业设置和平台运营；
- 任务协作、定时扫描、团队看板和从分析保存的持续监控；
- 多模型 LLM Runtime 与策略路由；
- Workflow + Autonomous Harness、长任务、Checkpoint/Resume、分布式 Worker/Sandbox；
- Context、Semantic、Knowledge、Tool/Skill/MCP、Action、Memory 全套治理；
- Trace、Replay、Dataset/Fixture、Multi-Grader、Regression Gate、Canary、Rollback；
- 正常、故障、演进三类可演示链路。

### 8.4 明确不在首版生产范围

- 替代企业现有数据仓库、BI 或主数据平台；
- 允许模型绕过 Query Gateway 直接访问生产数据库；
- 无审批的高风险资金、价格、库存或营销操作；
- 把模型生成内容视为法定财务报告或审计结论；
- 建设通用无行业边界的 Agent 平台；
- 首版提供原生移动应用或离线客户端；
- 默认将客户数据用于跨租户训练或优化。

## 9. 商业与运营假设

以下为产品规划假设，需在真实客户发现阶段验证：

- 采用 B2B SaaS 年度订阅，基础平台费叠加席位、Run、Sandbox 和模型用量；
- 企业版提供私有网络连接、专属密钥、区域部署、审计导出和高级 SLO；
- 用只读分析作为低风险切入点，以审批动作与周期任务提升留存；
- 采购决策涉及业务负责人、数据团队、IT/安全和财务，多角色价值必须在试点期同时被证明。

## 10. 成功指标

### 10.1 北极星指标

**每周被业务用户接受并形成后续行动的“可信分析 Run”数量。**

可信分析 Run 必须同时满足：任务完成、关键结论有有效证据、无权限或安全违规、用户确认可用，并至少被导出/分享、转为行动或纳入周期跟踪之一。

### 10.2 指标体系

| 维度 | 指标 | 首期目标/门槛 |
|---|---|---|
| 业务价值 | 从提问到首个可信结论的中位时长 | 相比人工基线降低 ≥ 50% `[待验证]` |
| 业务价值 | 被接受分析 Run 占比 | ≥ 60% `[待验证]` |
| 证据质量 | 关键 Claim 有效证据覆盖率 | ≥ 95% |
| 任务质量 | 核心 Eval Case Outcome 通过率 | ≥ 85%，关键场景 ≥ 95% |
| 安全 | 跨租户数据泄漏、未审批高风险执行 | 0（硬门槛） |
| 可靠性 | 可恢复长任务在注入故障后的完成率 | ≥ 99% `[课程目标]` |
| 运营 | Run 可解释率（可定位失败步骤与原因） | ≥ 95% |
| 成本 | 单个任务成本在租户预算内的比例 | ≥ 99% |
| 行动闭环 | 已批准行动获得执行回执与效果跟踪 | 100% |
| 记忆治理 | 删除后主库、索引、缓存残留召回 | 0（硬门槛） |

## 11. 演进路线与教学作用

| 里程碑 | 产品可见能力 | 核心工程增量 | 教学证明 |
|---|---|---|---|
| M0 业务基线 | 问题→分析→证据→报告→审批模拟 | 模块化单体、种子数据、Seed Eval | 先定义成功，再讨论架构 |
| M1 模型底座 | 多模型策略、调用成本与失败解释 | LLM Runtime、Capability、Routing、Attempt | 模型调用是可治理执行单元 |
| M2 可靠执行 | 异步 Run、时间线、中断恢复、审批 | Harness、Workflow、Checkpoint、Queue、Sandbox | Agent 是有状态长任务系统 |
| M3 数据与能力治理 | 指标、证据、动态工具、受控 Action | Context/Semantic/Tool/Skill/MCP/Action | 能力必须有契约、权限和证据 |
| M4 可信记忆 | 偏好延续、记忆查看/修正/删除 | Memory Policy、Write/Recall/Delete | 记忆有用且不替代权威事实 |
| M5 受控进化 | 版本对比、门禁、灰度、回滚 | EvalOps、Replay、Regression、Canary | 优化必须有可复现证据 |

## 12. 核心不变量

1. 任意数据对象、Run、Artifact、Memory、Action 和 Trace 都可唯一归属到租户与授权主体。
2. 租户授权由服务端建立；界面选择、模型输出和普通请求参数不可覆盖该上下文。
3. 高风险 Action 在审批前不得产生真实副作用，批准后只能执行审批过的不可变版本。
4. Retry/Resume 不得重复提交已成功的 Action；每次提交必须有幂等键和可验证回执。
5. 关键经营 Claim 缺少有效 Evidence 时，不得标记为“已证实”。
6. Memory 不保存实时经营值、权威指标定义、凭据、原始敏感数据或历史授权。
7. 取消、超时、配额耗尽和关键上下文缺失必须具有明确状态；可恢复等待与执行终态分开，保留已完成产物并说明未解决目标。
8. 任意候选版本未通过安全硬门槛时，不得因平均质量分提升而发布。

## 13. 风险与应对

| 风险 | 影响 | 产品控制 |
|---|---|---|
| 错误口径产生看似合理结论 | 错误经营决策 | 口径确认、Semantic Registry、数据质量与 Claim-Evidence |
| Prompt/文档注入影响行为 | 越权或错误行动 | 指令/数据分离、信任分层、工具白名单、输出校验 |
| 跨租户泄漏 | 严重安全与合规事件 | 端到端 Tenant Context、隔离存储、负向测试、硬发布门槛 |
| 长任务失控 | 成本、延迟、资源挤占 | Autonomy Budget、Deadline、配额、停止条件、取消与接管 |
| 副作用重复或篡改 | 真实业务损失 | Proposal 冻结、审批、幂等、短期凭据、验真和补偿 |
| 记忆污染或过期 | 长期行为劣化 | 写入策略、来源校验、版本/TTL、修正删除、Memory Eval |
| 模型/策略升级静默退化 | 生产质量下降 | 版本元组、Fixture、Regression Gate、Canary、Kill Switch |
| 教学项目过度平台化 | 学习曲线与交付风险 | 每阶段一条可验收垂直切片，稳定契约、渐进拆分 |

## 14. 决策与开放问题

### 14.1 已确定决策

- 以零售经营分析为业务域，不扩展为通用 Agent Builder。
- 先只读分析、后受控行动；高风险动作默认人工审批。
- 普通用户默认首页采用 Intent-first 经营分析入口，不以固定 BI 看板作为产品入口。
- 产品按经营分析、企业设置和平台运营分区；导航与能力由当前角色和租户策略编译。
- 证据链、Run Timeline 和租户边界属于首版产品能力。
- 原型不绑定生产技术栈，不通过外部 CDN 获取运行依赖。

## 15. 产品定义完成标准

- 产品定位、用户、价值、范围和成功指标能支撑课程定义的 DataAgent 场景；
- 产品范围与课程承载矩阵分离；课程能力不要求逐项对应页面或一级导航；
- M0 先证明一个真实纵切可用，后续能力必须由使用证据、风险或规模约束触发；

- 安全、证据、审批、恢复和发布门槛被定义为产品不变量；
