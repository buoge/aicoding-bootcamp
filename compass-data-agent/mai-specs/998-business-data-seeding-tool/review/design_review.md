## 1. 总体判断

这套材料适合作为**业务规则参考和扩展版数据生产蓝图**。整数分、部分退货、收入与现金分离、库存守恒、多租户复合键、业务时间与可知时间、独立金标等设计值得保留。附件也明确区分了设计、小样验证和未实现能力；本次复跑证实了其小样验证结果。

当前实施路线同时承担了 C# 定制生成器、Python 经营模拟器、双存储与双引擎验收、历史查询代理、复杂检查点和百万数据发布。对 998“方便准备数据并导入数据库”的目标，交付链过长。与此同时，63 张表仍缺少 999 中几个关键分析场景的专用输入，不能以表数或订单量代表产品覆盖。

原评审提出以下方向；数据库环境方向已获后续确认，其余取舍继续保留建议状态：

1. **首版以 PostgreSQL 可直接导入的数据包为主交付**，优先复用现有 Python 工程。生成、校验、导入可分别执行，也提供一个组合入口。
2. **保留百万订单作为扩展配置**，同时提供固定边界样例和日常开发配置；先确定它与 999 的演示版、云端版容量目标的关系。
3. **按产品场景组织数据能力**：共享零售事实，额外提供清洗、对账、预测、实验、因果和监控的小型场景附件。
4. **先降低生产复杂度**：减少全时期快照、跨语言中间协议和非必要恢复机制；金额、库存、身份、时间及证据约束持续保留。

本次未发现已验证的小样数值计算失败，也没有证据支持宣称全量方案已经可用。以下 P1 项是进入实现前应收敛的问题；没有把未经批准的远期容量或全部 108 项平台功能列为 998 首版硬门槛。999 当前本身处于 `review`，本报告按其最新有效规格作对照，不能代替负责人批准。

## 3. 关键发现

### R01 · P1 · 规模与时间缺少统一的交付配置

**证据：** 999 PRD §15.1、§15.3 定义完整企业画像为主租户约 8,000 SPU / 60,000 SKU / 240 门店 / 8 配送中心，演示 10 万订单、课程云端 1,000 万订单。998 主方案 §3 为主租户 600 SPU / 4,800 SKU / 24 门店 / 3 配送中心，三个租户共 100 万订单。998 订单截至 2025-12-31；原型 `scenarios.js` 第 23–34 行主要使用 2026 年秋季窗口。

**触发与影响：** 直接连接原型的日期参数会得到空结果；直接把百万版称为 999 的完整课程数据，会让容量验收和企业画像互相冲突。缩小规模本身合理，当前缺少的是显式映射。

**最小修正：**

- 登记 `fixture / dev / demo / extended-1m` 等配置的用途、订单头数、主数据量、日期、场景、资源预算；名称属于本报告建议。
- 999 的 10 万演示目标可作为 `demo` 候选；日常 `dev` 可更小。百万版作为独立扩展，暂不冒充千万云端版。
- 在“保留 2023–2025 数据并统一原型/任务参考时钟”与“重新生成匹配原型日期的数据”之间作一次明确选择。建议优先保留冻结历史窗口，应用显式展示数据参考时间，减少随机器日期漂移的维护成本。
- 预测、同比、复购和尾窗分别声明可用区间；不能把 2026 Q1 无新单尾窗解释为经营衰退。

**验证：** 每个入选场景的日期在发布清单覆盖范围内；相对时间解析得到可用窗口；同比有基期，复购队列成熟，预测测试窗不进入尾窗。

### R02 · P1 · 主交付偏向分析文件，数据库导入的可操作契约不足

**证据：** `profile_1m.yaml` 设置 `facts_in_full_pg_load: false`；主方案 §5.4 把 PostgreSQL 全量装载列为对照路径。生产细则 §11.3 已提出 staging、按 run/tenant/partition 幂等和失败不覆盖旧版，但具体导入工具尚未实现。DDL 固定 `core/ops/sec/eval` 名称，H02 又要求数据库内恰好一个 release。

**触发与影响：** 使用者拿到 Parquet 和 DDL，仍无法完成“导入当前项目并验证可查”。若实现时随意拼接 staging schema、现有 `core` 表和多版本数据，容易遇到主键冲突、权限部署错库、半成品可见或多个 release 混入单版本模型。

**最小修正：**

1. 首版明确“数据包 → PostgreSQL 零售分析库”为正式支持路径，输出表清单、版本、字段顺序、行数和哈希。
2. 导入前检查目标库、schema 版本、已有 release、文件完整性及依赖；默认拒绝向不兼容或未知非空目标追加。
3. 同一 release 同一内容再次导入必须幂等；同 ID 不同内容必须失败。分区提交、中断重试和验收失败的处理规则分别写清。
4. 选定一种发布方式。对于当前“一库一 release”模型，推荐先装载到独立候选数据库，校验后切换零售数据连接；平台业务库保持独立。切换时冻结新运行所用 release，旧运行继续绑定原版本。若选择 schema 切换，则须实现 schema 参数化和依赖重绑定，不能只改 `search_path`。
5. 保留上一份可用 release；清理操作必须明确指向工具管理的数据范围。

**验证：** 空库成功、同包重复、同 ID 异内容、错 schema、坏文件、导入中断、两个导入并发、发布失败及回切旧版。当前附件尚无这些端到端证据。

导入可采用客户端流式批量装载。PostgreSQL 17 `COPY` 的原生格式为 text/csv/binary，Parquet 需要转换或读取适配；`STDIN` 可通过连接传输，避免要求用户把文件搬进数据库容器。加载账号与业务只读账号应分离，启用 RLS 的装载路径要专门验证。[PostgreSQL 17 COPY 文档](https://www.postgresql.org/docs/17/sql-copy.html)

### R03 · P1 · 八个经营情节与十二个产品场景混用了编号，且覆盖不完整

**证据：** 998 `scenarios.yaml` 的 S01 是“大促增长与毛利承压”，S08 是“权限绕过”；999 的 S01 是“快速问数”，S08 是“随机实验”。当前 30 道题以经营 SQL 为主，没有随机分流数据、清洗源文件和完整预测回测资产。

**触发与影响：** 用 `scenario_id=S08` 连接原型、生成器和 Eval 时会选错题；即使所有现有题通过，仍无法验证 AC-S03、AC-S07、AC-S08、AC-S09 等。

**最小修正：** 新执行规格分别使用产品任务 `S01–S12`、数据情节 `D01–D08`、评测题 `Qxx`，用映射关联。原始材料的 S 编号保留在来源记录。每个产品场景登记需要的数据、参考时间、授权身份、独立预期与不足时应有的结果。第 4 节给出逐场景清单。

**验证：** 每个声明支持的产品场景至少有一个成功或明确不足的可执行样例；未支持场景标为未覆盖，不能借用同号情节宣称通过。

### R04 · P1 · Contoso 双语言改造的必要性需要重新确认

**证据：** 生产细则 §§2–7 规定 Contoso 导出权重/候选，Python 管理主数据、上下文和全部业务过程，包含 10 份中间资产及跨语言随机协议。当前项目已有 Python API 与工具链。固定上游项目确实使用 `net8.0`，并包含 Windows 风格的 PreBuild 命令。[固定提交项目文件](https://raw.githubusercontent.com/sql-bi/Contoso-Data-Generator-V2/eaeb57a9eaa6ad0cdab4fb527552102685434ee0/DatabaseGenerator/DatabaseGenerator.csproj)

**触发与影响：** 若“必须基于 Contoso”没有独立教学或来源要求，为权重与购物篮维护 C# fork、Python 双向文件协议和构建链，会先消耗大量工程投入，核心经营逻辑仍须自行开发。

**最小修正：** 优先建议单 Python 生产者，以配置表达季节性、长尾与购物篮分布，保留独立 SQL 验证。材料已把 Contoso 复用写成来源要求，因此这项是**待负责人确认的删减建议**；未经确认不能删除来源要求，独立生成的数据也不能继续标为 Contoso 派生数据。若必须复用，先验证固定源码在目标环境能构建和产出一份候选，再进入业务模拟。

**验证：** 用相同小样目标比较实现范围、可复现性、源码来源与开发环境负担。不要用尚未实现的 fork 作为现成能力估算排期。

### R05 · P1 · 库存快照主导体量，应先优化物化范围

**证据：** 主方案 §3.3 估算数量与估值快照各 29,412,800 行，两者合计 58,825,600 行；订单头只有 100 万行。方案已避免 SKU×全地点笛卡尔积，也已限制为一套最终重述快照，这些既有减法应保留。

**触发与影响：** 即便只减少订单数，完整 36 个月的 SKU×地点日快照仍可能很大。按快照规模直接引入双引擎、文件权限和检查点，会增加数据库初始化工具的建设成本。

**最小修正：**

- `dev` 联动缩小 SKU、地点及会员池，不能只缩订单数。
- 保留库存流水作为重算依据；默认仅物化场景需要的日期、经营组合和库存周转窗口。需要完整长期日均库存时再扩展，不能省掉计算所需观察点。
- 同一知识截止的数量与估值尽量在一次重放中计算。数据库可继续分表以保留成本权限；不要为了少一张表破坏现有授权边界。
- 对“库存为零”“地点未经营该 SKU”“数据未到”使用不同语义；稀疏存储不能把三者合并。

**验证：** 小样重放与物化结果一致；目标查询无缺失日期，缺货持续时间和库存周转分母不变；再实测导入量与查询耗时决定是否引入 Parquet 全量查询。

### R06 · P1 · 总行数充足不保证场景样本密度

**证据与推算：** 主租户 90 万单 / 1,096 天，平均约 821 单/日。按 POS 14% 权重和 24 家门店粗估，约 4.8 单/店/日；按小程序 18%、华东 29% 粗估，约 43 个创建订单/日，均摊每五分钟约 0.15 单。这里未考虑时段、季节、开店日和支付重试，仅用于暴露稀疏风险，不是生成结果。

原型 S11 要演示“小程序支付成功率低于 95% 持续五分钟，再恢复”；配置的 `payment_success_probability_after_reserve=0.94` 也不能直接当作原型 98% 左右正常基线。每次尝试成功率与订单最终支付成功率需要先统一定义。

**影响：** SKU 缺货、同店增长、留存和分钟监控可能样本过少；极端比率来自一两单，教学结论不稳定。单纯增加全库订单量会把无关库存和行为数据一起放大。

**最小修正：** 为每个教学切片声明最低样本条件，提供有背景数据的定向场景；S11 单独生成固定短窗口的高密度支付尝试与故障事件，且与对应订单、租户、渠道关联。低分母时输出“样本不足”。实验不必强行使用原型的 5 万人/组，但要足以验证指定统计流程。

**验证：** 在最终 release 上报告每个场景的有效样本数、成熟度、正常/异常/恢复段；稀疏组及缺数据分支有明确预期。

### R07 · P1 · 业务模型丰富，但面向产品的分析契约仍薄

**证据：** 当前只提供 `mart.sales_daily`、`cash_daily`、`order_state_at` 三个函数；原型还引用 `authorized_member_sales`、`retention_by_cohort@v3`、固定对账快照等逻辑资产。`core.customer.segment_code` 定义为“固定初始分群”；999 S02 需要随分析窗口变化的新老客。999 §15.2 的净销售额还允许业务发生口径与原订单群回溯口径分别选择。

**触发与影响：** 实现者容易直接用固定分群当新老客，或用事件日净销售替代原型回溯口径；同一页面可出现“SQL 正确、业务解释错误”。有订单和 customer_id，也不自动得到正确的留存矩阵。

**最小修正：** 为入选场景补薄查询层和指标说明，优先定义以下内容：

| 分析资产 | 必须说清的语义 |
|---|---|
| 净销售、GMV、现金、毛利、渠道贡献 | 确认事件、退款归属、单位、成本权限和缺报；支付总额不能替代交付收入 |
| 新老客、复购、留存 | 首购以支付还是交付判定、首购可观察边界、退款处理、未知会员、成熟度、筛选前后分母 |
| 同店增长 | 两期共同经营门店集合；仅开闭店日期不能描述临时停业，首版可明确不模拟临时停业 |
| 退货率 | 订单/单件/金额分别定义；30 日窗口与未成熟队列单列 |
| 库存风险 | 可售实物、预留、可承诺、在途、快照截止；不能重复扣预留 |
| 监控支付成功率 | 尝试还是订单口径、重试去重、滑动窗口、最小样本数、来源完整性 |

按场景建立少量 SQL/视图/查询模板即可，不要求在 998 内重建通用语义平台。每个模板绑定 release、指标版本、三个时钟和权限范围；原型的参考金额应由所选数据包算出，静态演示数字不作为必须拟合的真值。

**验证：** 相同过滤条件下，答案卡、趋势、明细、看板及金标能对账；固定初始分群和按窗口计算的新老客不混用；未成熟留存单元格返回不可用，不能补成 0。

### R08 · P1 · 小样、规范模型和产品场景之间仍缺一层真实贯通验收

**证据：** 八单验证采用独立 `validation_fixture` 模型；规格验证只填充部分规范表。主方案 §11.1 已承认 FIFO、完整状态机、库存重放、恢复和查询代理仍须实现。`tools/build_acceptance.py` 第 10–18 行将 H01 配额和 H02 日期写死为百万版。

**触发与影响：** 新增小规模配置后，如果复用硬编码断言，会把合法小样判为失败；若为绕过失败关闭门禁，又可能放过真实错误。独立金标通过也不能发现规范装载映射错列或导入漏表。

**最小修正：**

- 让配额、日期、启用场景和允许空资产来自已冻结 profile，断言规则本身保持独立。
- 将固定边界样例经真实生成/装载入口写入规范模型，再用独立查询与固定预期比对，保留原八单数学样例作为另一条验证路径。
- 增补跨区域销售与退货、非零调拨在途、缺货失败释放、零库存、广告缺报、会员晚绑定及同 ID 异租户的规范样例。
- 声明支持的每个产品场景都要有可执行金标或边界判断；30 道题的 `gold_query_design` 当前主要是查询设计，仍需物化到选定 release。

**验证：** “生成 → 包校验 → 导入 → 只读查询 → 独立预期”完整运行；记录输入版本与通过范围。基于同一函数重复计算两遍不构成独立核对。

### R09 · P1 · 应复用 999 的查询与权限边界，避免建立第二套平台

**证据：** 999 技术方案 §7 已规定平台库与零售分析源分离，Query Gateway 负责安全查询，Sandbox 消费授权快照。998 又设计 AsOf broker、独立身份映射、连接池、快照与缓存。当前 RLS 使用 `session_user`，一个数据库登录只映射一个 tenant；999 的产品用户可加入多个租户并动态切换授权。

**触发与影响：** 若把这些功能全部放进造数工具，会出现两个身份/权限真源；若用现有管理员连接统一执行，再让模型填写 tenant，附件的安全假设也不成立。

**最小修正：** 998 交付隔离的业务数据、最小测试角色/授权样例、字段分类和时间契约；999 的网关负责从认证用户映射到受信任的数据读取上下文。固定教学身份可以先用有限数据库角色，但需说明它与产品动态授权的映射和撤权验证责任，避免为每次运行创建完整身份系统。

评测答案、场景参数、master seed 和未授权文件继续隔离；平台审批、Run、Memory、Artifact、通知、预算执行等状态由产品管理，998 仅在需要时提供种子配置，不复制完整平台表结构。RLS 的超级用户/BYPASSRLS 绕过边界确实存在，不能把 `FORCE RLS` 当成管理员连接的保护措施。[PostgreSQL 17 行安全文档](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)

**验证：** 同一教学身份在业务查询、历史快照、图表导出和缓存命中中拥有一致范围；被撤销权限不能因已有快照继续读取；数据包导入账号不可被 Agent 使用。

### R10 · P2 · 边缘状态、检查点及产物格式可以分阶段交付

**证据：** 原方案同时设计跨仓整单原子预留、FIFO、RTO、拆单支付、损坏/报废、每天状态检查点、跨 worker 复现，以及多种图源与完整 HTML。

**影响：** 这些能力各有价值，全部成为首版入口条件会推迟可用数据。部分能力对应当前验收，另一些只是提高模拟器完整度，须分别处理。

**建议：**

- 保留部分退款、跨期交付/退货、原成本追溯、库存调拨/报损、租户隔离等 AC-DATA 明确要求。
- RTO、复杂多仓路由和随机化的拆单支付可先作为固定边界 fixture，待相应题目进入大样正式覆盖再扩展成常规随机路径。Q22 等仍需保留可核验样例。
- 若 `dev/demo` 实测重跑成本可接受，先支持整次确定性重跑和导入幂等；等百万生成时间及中断成本明确后，再实现完整事件队列检查点。省略断点恢复时要声明“失败后重跑”。
- 初期一个权威模型、一种导入格式、一份说明和必要关系图即可；SVG/PNG/DOT/HTML 等作为派生产物按需生成。

**验证：** 任何减法都逐项核对受影响 Q 题和 AC；被延后的生成路径不能继续标为该 profile 已支持。恢复的退出条件由实测成本触发，不以任意订单阈值替代。

## 4. 对照 999 的十二类场景

下表评价的是**数据支持程度**；产品编排、界面和模型能力仍由 999 实现。标“有基础”只表示已有设计资产，不代表生成器已交付。

| 产品场景 / 验收 | 当前覆盖 | 最小补充与原因 |
|---|---|---|
| S01 快速问数 / AC-S01 | 收入/成本/现金及 Q01、Q04 有基础 | 补与原型绑定的日期、净销售口径和查询入口；提供正常、真实零、空窗口、晚到、无权五种结果 |
| S02 交互探索 / AC-S02 | 渠道、商品、会员、同店相关事实与 Q03 有基础 | 新老客按选定窗口计算；保留未知身份；用同一组明细验证下钻加总、同比和同店分母 |
| S03 文件清洗 / AC-S03 | 有会员/订单，没有活动名单输入附件 | 增加可关联的脏 CSV、重复键/缺失键/无订单会员和干净预期；一份小文件即可，无需新建清洗服务 |
| S04 对账调查 / AC-S04、AC-DATA-01/07 | 八单现金/收入差异和迟到重述有基础 | 增加两份固定来源快照、各自口径及差异明细，含可解释项和残差；不同来源仍要从同源事实派生 |
| S05 异动诊断 / AC-S05、AC-DATA-04/05/06/08 | 缺货、退货、流量、开店、迟到情节较完整 | 增加“支持/反证/证据不足”样例和情节作用范围；确保小样保留目标 SKU 与足够样本，因果结论限于可识别证据 |
| S06 深度专题 / AC-S06 | 订单、库存、流量可支持若干分支 | 补少量关联日期/对象的活动说明、补货通知、服务发布记录等合成业务文档；若演示移动端耗时分支，再补相关可观测字段/附件，否则明确该分支证据不足 |
| S07 12 周预测 / AC-S07、BR-D03 | 有 36 个月计划历史，没有可执行回测数据约定 | 固定多个 12 周回测窗、训练可知截止、未来已知计划、库存约束及销量定义；评测未来标签私有，排除尾窗断供造成的假趋势 |
| S08 随机实验 / AC-S08、BR-D02 | 缺实验设计、随机分配和曝光/结果链 | 增加实验定义、分配记录、曝光与结果关联，含未转化受试者、样本失衡反例、退款护栏；仅营销活动表不能重建随机实验 |
| S09 观察性因果 / AC-S09、BR-D02 | 有价格/订单，没有指定人群的干预设计与前趋势样例 | 增加干预时点、处理/对照人群、可观测混杂与成熟结果窗口；至少提供前趋势失败样例，正确结论允许“无法确认因果”，无须首版建设通用因果模拟器 |
| S10 周期报告 / AC-S10、AC-DATA-07 | 有业务历史、水位、Q26 | 提供按固定时钟推进的数据到达版本/脚本，覆盖正常、迟到、补齐；投递回执与调度归产品执行，造数工具不伪造已投递 |
| S11 主动监控 / AC-S11 | 有支付尝试，现有 Q27 演示的是日销售告警 | 补分钟级支付异常/恢复、故障凭据、最小分母、阈值边界与检测源缺失样例；事件去重和冷却由产品验证 |
| S12 留存看板 / AC-S12 | 有会员/订单、30 日复购题 | 补可复算 cohort×相对月份结果，定义首购/活跃/退款、未知身份和未成熟单元格；区域/渠道过滤须遵循授权及固定 cohort 定义 |

**AC-DATA-01–10 的覆盖判断：** 01–05、07–09 已有较强规则设计，仍缺规范模型完整装载与产品消费验证；06 已有新店/同店情节，应补共同门店集合与样本检查；10 的合成标识和“未生成全量数据”边界在材料中已有明确说明，应继续保留。

原型 S04 还出现“固定汇率快照”的演示文案，而 999 §15 与当前方案均以 CNY 单币种为默认范围。建议后续调整该示例，把差异来源限定在退款归属、延迟、过滤或费用口径；本次无需为了这句原型文案增加多币种系统。

## 5. 可以怎样简化模型和工程

### 5.1 保留业务含义，按消费场景启用资产

不建议单凭“63 张表太多”制定一个新的表数指标。主外键已经把订单、单件、支付、库存、售后串成闭环，随意删除中间表容易破坏可追溯性。先减少要模拟的状态和要物化的数据，再根据场景依赖决定保留哪些表。

| 资产/能力 | 建议 | 理由与恢复条件 |
|---|---|---|
| 租户、渠道、区域、地点、SPU/SKU | 保留；按 profile 缩小记录量 | 多租户、规格缺货、跨区域履约直接依赖 |
| 品牌/品类/运动标签 | 维持简单字典及必要关联 | 支持产品探索；无须额外引入通用主数据平台 |
| 价格/成本版本、渠道 SKU 映射 | 保留最低有效版本和历史快照 | 原订单价格与成本可追溯；复杂版本变更只对测试场景生成 |
| `order_header/line/unit` | 首版继续保留 | 单件金额、部分退货与原批次成本已有完整约束；改成数量分摊可能减少行数，但会重做大量契约，当前收益未证实 |
| 优惠与退款分摊 | 保留；普通样本限制优惠组合数 | 整数分和部分退款是明确要求；促销规则引擎可延后 |
| 支付/履约/退货/财务事件 | 保留核心路径，边缘路径用固定样例 | 区分现金、收入、原成本；避免随机状态组合爆炸 |
| 库存批次与流水 | 保留简化 FIFO 和可重放事实 | 库存守恒、原成本、跨地点转移需要证据；不建设完整仓储系统 |
| 两类日库存快照 | 场景窗口按需物化，一次重放生成 | 控制主要数据体量；完整历史窗口需要时再扩展 |
| 会员与身份绑定 | 保留可空身份及最小晚绑定样例 | 防止跨渠道虚构统一用户；无须复杂身份解析服务 |
| 自有行为、平台日报、广告 | 分域按需启用；保留来源边界 | 自有漏斗与平台聚合不能混接；广告是既有产品数据域，三行选做 CSV 不足以据此整体删除 |
| 月目标 | 保留简单月×渠道×区域版本 | 支持经营问答；实际预算调整动作另归产品能力 |
| 发布清单、哈希、质量报告 | 保留最小集合 | 可定位导入的数据和失败原因；不扩展为通用资产目录平台 |
| `sec` 授权样例 | 提供少量确定性身份 | 验证租户/区域/成本差异；平台认证管理由 999 负责 |
| `eval` 真值与题目 | 初期可用独立受控文件包 | 不必为离线金标额外建设管理后台；答案与业务数据必须隔离 |
| 双引擎全量校验、动态 AsOf 沙箱 | 延后到真实消费需求触发 | 首版可用 PostgreSQL 只读模板与少量固定历史快照；字段时间语义保留，不能据此声称支持任意历史 SQL |

可选域必须具备依赖闭包。例如去掉广告数据后，“渠道贡献”不能继续按总费用完整输出；删除库存事实后，缺货诊断应标未支持。仅把表留空并让查询返回 0，会掩盖能力缺失。

### 5.2 首版建议的操作闭环

以下是待设计的行为，不是现成命令：

```mermaid
flowchart LR
    A["选择 profile、seed、业务日期"] --> B["单一生成器<br/>共享业务事实 + 场景附件"]
    B --> C["数据包与清单<br/>版本、行数、哈希、时间"]
    C --> D["独立校验"]
    D --> E["导入候选 PostgreSQL 零售库"]
    E --> F["查询与权限验收"]
    F --> G["切换可用 release"]
    G --> H["Compass 查询与演示"]
```

建议先提供 CLI，支持“生成包”“检查包”“导入包”和组合执行。控制参数仅暴露场景、规模、seed、日期与目标连接引用；复杂分布放版本化配置。先交付一种稳定导入格式，用户自带任意 CSV/Excel 的通用映射导入可另立范围。

文件清洗场景的 CSV 是业务输入附件，与工具的内部数据库装载格式分别管理。模拟源数据错误也单独保留脏输入及预期诊断，不能让规范事实库违反所有硬约束来制造“真实感”。

## 6. 需要补齐的最小规格

| 规格项 | 建议写入内容 | 为什么必须明确 |
|---|---|---|
| 交付配置 | dev/demo/扩展版的实体规模、日期和场景支持矩阵 | 控制开发成本，避免小样与容量版混用 |
| 导入契约 | 支持数据库、迁移归属、目标识别、幂等键、冲突规则、错误退出、发布/回切 | 直接对应 998 的使用目标 |
| 数据包契约 | schema/generator/profile/scenario/metric 版本，seed、时间、表行数、哈希、依赖、质量结论 | 导入器与生成器能够独立验证和复现 |
| 最小业务查询 | 指标 ID、公式、粒度、时间、身份、空值与零值、预期结果 | 产品能消费模型，不必直接理解所有底层关系 |
| 场景附件 | 清洗 CSV、双侧对账快照、业务文档、实验分配、因果人群、监控事件、预测切分 | 补足“表多但任务缺输入”的问题 |
| 业务样本质量 | 场景分母、成熟度、有效关系、预期方向/反例和容差 | 保证低规模配置依然可演示、可评测 |
| 权责边界 | 998 数据生成/装载，999 查询授权/运行/审批/产物；测试身份映射 | 避免出现第二套平台和权限真源 |
| 资源验证 | 样本生成时间、峰值内存、包大小、导入/索引耗时、核心查询耗时 | 用实际测量选择存储及恢复策略 |

预算调整 CAP-06 当前为选做。若以后纳入 998 支撑范围，应补 campaign 预算计划与版本，供产品演示调整草稿；审批、幂等执行和回执继续由 Action Runtime 验证。CAP-08 的 MCP 只需消费同一查询契约，无需再造一份数据。

## 7. 建议的验收与实施顺序

### 7.1 修订后的最小验收清单

这些是本次建议，尚未成为新增的已批准 AC；已有 AC ID 保持不变。

| 顺序 | 验证闭环 | 通过证据 |
|---|---|---|
| 1 | 固定边界样例 → 规范模型 → 独立查询 | 金额 0 分差异；无孤儿/跨租户引用；部分退款与跨期事件逐项一致 |
| 2 | 库存关键链 | 预留、释放、发货、退货、调拨、报损及原成本可重放；快照一致，正常中间事务不误判 |
| 3 | 数据包 → 干净 PostgreSQL → 应用查询 | 使用公开入口一次完成，金额单位/时区一致，原 demo 链路有明确兼容策略 |
| 4 | 重复与失败 | 同包幂等、冲突拒绝、坏文件不发布、中断可按承诺方式恢复、旧版仍可查 |
| 5 | 身份与历史时间 | 租户/区域/成本正负例；迟到前后不同结果；未来身份、价格和私有金标不泄漏 |
| 6 | 产品数据场景 | 入选 S 场景及 AC-DATA 各有输入、参考查询/算法和预期；零/空/迟到/无权/不足可区分 |
| 7 | 小规模性能 | 在目标开发环境测量生成、装载、查询及磁盘；不预先承诺未测吞吐 |
| 8 | 百万扩展 | 配额精确、全域硬约束、分布与情节报告、确定性重跑；声明支持断点恢复时另测中断恢复 |

复购、预测、实验与因果题需要方法和数据前提检查，不能全部转成“答案金额相等”。模型生成的 SQL 不充当唯一金标，参数里写的概率也不充当实际观测效应。

### 7.2 建议分三步

**第一步：收敛契约。** 解决 R01–R04、R07、R09：确定当前 profile、日期、生成器来源要求、数据库路径和首批产品场景。产物为修订后的 998 有效需求/设计及 S–D–Q 映射。保持原始 context 不变。

**第二步：完成最小真实链路。** 先让固定样例经生成/装载入口进入规范 PostgreSQL，再打通净销售问数、对账、库存缺货与一个隔离负例；补齐导入失败处理与重跑。由此暴露真实模型和接口成本，再扩展共享数据。

**第三步：补全场景，再放大规模。** 增加清洗、预测、实验、因果、周期和分钟监控附件；按承诺范围执行验收。百万配置随后放大，只有测量表明单库或重跑成本成为瓶颈时，再引入列式分析链与完整检查点。

这里的先后顺序不删除 999 的完整产品目标；只将数据工具的交付依赖组织成可检验的小步。
