## 二、这版项目的业务与规模已经固定

### 1. 业务选择：中国全渠道运动户外品牌集团

主租户设定为一个虚构的运动户外集团，经营大众运动、专业跑步和户外品牌。

商品覆盖八个一级品类：

- 运动服饰、运动鞋履。
- 户外露营、包袋配件。
- 健身训练、骑行装备。
- 水上运动、护具与运动小件。

这些品类可以自然产生不同的规格体系：鞋码、服装尺码、颜色、容量、重量和型号。对应的经营问题也有足够差异，例如核心尺码缺货、换季清仓、夏季需求、搭配购买、物流费用和退货。

渠道固定为天猫、京东、抖音、小程序、APP、普通门店和奥莱，覆盖中国七个经营大区。

**销售渠道、获客来源、下单门店、履约仓店、销售归属区域、实物所在区域分别建模。** 例如，华东顾客通过 APP 下单，由华南仓发货，再到华东门店退货，销售归属与库存归属仍然能够分别对账。

### 2. 三个租户的规模

| 项目         | 主租户 101 | 租户 102 | 租户 103 |          合计 |

这些是**课程合成配置**。两个辅助租户拥有独立的商品、价格、客户、采购和库存过程，用来验证企业之间的数据隔离。

时间范围为：

- **下单期：2023 年 1 月 1 日至 2025 年 12 月 31 日，共 36 个月、1,096 天。**
- **生命周期尾窗：2026 年第一季度，共 90 天。**

尾窗继续处理年末订单的履约、退货、退款及数据迟到，支持同比分析，也避免为了截断日期而提前“完成”业务事件。

### 3. 百万订单的计数口径

订单创建成功后，即使后来支付失败、取消或退货，仍然属于这 100 万单。

生成流程采用：

> 创建订单 → 异步尝试整单锁库 → 支付 → 履约 → 售后。

库存不足会产生真实的锁库失败和取消记录，保留其经营影响。订单总数通过前置配额算法精确控制，后续状态由业务过程决定。

### 2. 为什么设计“订单头 → 订单行 → 逻辑单件”

部分履约、部分取消和部分退货，都需要精确到数量中的某一件。

例如，一行订单购买三件商品，后来只退一件，系统需要知道：

- 这一件分摊了多少优惠。
- 这一件来自哪个库存批次。
- 这一件原来的销售成本是多少。
- 退款对应哪笔原支付。
- 收入、现金和成本分别在哪一天变化。

因此模型引入了 `order_unit`。它是**逻辑计量与会计单位**，用于建立可核对的业务关系。

## 五、方案重点解决了六类容易让数据“看起来正确、实际对不上”的问题

### 1. 金额分摊和资金对账

所有金额采用 **人民币、不含税、整数分**。

优惠必须分摊到逻辑单件，并保证订单头、订单行、单件和优惠分摊总额一致。例如，100 分分给三件商品，确定性分配为：

**34 分、33 分、33 分。**

支付、退款还要分别满足原支付上限、订单上限和单件退款依据，重复成功回调不能重复记钱。

### 2. 收入、现金和成本分别记录

本课程冻结的经营口径为：

| 业务事件 | 对应影响                     |
| -------- | ---------------------------- |
| 支付成功 | 增加收款现金                 |
| 商品交付 | 确认收入和原批次销售成本     |
| 接受退货 | 冲减原单件收入               |
| 退款成功 | 减少现金                     |
| 可售回库 | 冲回原销售成本               |
| 判定损坏 | 保留原销售成本，记录损坏实物 |

这样可以回答“销售已经下降，为什么退款现金还没发生”“退款完成了，为什么毛利还没有完全恢复”等跨期问题。

### 3. 库存由业务事件推导

库存明确区分五个桶：

**可售实物、隔离库存、损坏库存、预留库存、在途库存。**

其中：

`可用数量 = 可售实物数量 − 预留数量`

库存由期初、采购、调拨、预留、出库、退货收货、可售回库和报废等事件推进，并采用 FIFO 批次成本。

退货链也进行了严格限定：实际收到退货时，在接收地点建立退货批次；待检、恢复可售和判损沿用这个批次，成本追溯到原发货批次。整单跨仓预留则作为一个原子事务提交。

### 4. 历史经营分析使用三个时钟

方案分别建模：

- **业务时间**：事情实际发生的时间。
- **可知时间**：数据进入分析系统、可以被查询到的时间。
- **语义时钟**：解释“昨天”“上个月”等自然语言的固定参考时间。

例如，一笔交付发生在 12 月 31 日，但记录在 1 月 2 日才到达。元旦当天的报表与后来重述的 12 月报表，可以得到不同且各自正确的结果。

这对课程尤其有用：即使系统运行在更晚的年份，也可以固定历史参考时间，让 Agent 稳定回答同一道题。

### 5. 权限作用到事实、指标和缓存

租户、区域和成本权限由受信任身份绑定。销售按原订单经营区域授权，库存按实物地点区域授权。

数据库部分提供可执行权限策略；Parquet 分析部分则要求查询代理实施对应的文件、关系和时点控制。权限范围也进入缓存键，避免不同身份复用不适用的结果。

无成本权限时，毛利返回不可用状态；广告报告缺失时，经营贡献不能把缺报当成零投放。

### 6. 可复现与失败恢复

方案固定了命名随机流、稳定业务键、确定性 ID、事件排序和检查点协议。

同配置重新运行或中断恢复，应得到一致的业务结果。检查点保存库存五桶、FIFO 批次、预留归属、未完成订单、未来事件队列、ID 分配状态和已提交分区。

正式发布采用不可变版本和最后提交的完整清单，能够追溯每份数据的来源、参数和质量结论。

## 六、容量与 Data Agent 的使用场景也已经纳入

### 1. 全套数据规模会明显超过百万行

**100 万是订单头规模。**

按照方案中的参考经营组合，单版本库存数量快照约为：

**24,800 个 SKU × 地点组合 × 1,186 天 = 29,412,800 行。**

库存估值快照另有一张同粒度表，两张快照的参考行数合计接近 5,900 万。再加上交易、状态和行为，全套资产预计达到上亿行量级；实际规模由试产和最终清单确认。

因此推荐：

- PostgreSQL 管理控制信息、权限和规范验证。
- 不可变 Parquet 保存全量事实和快照。
- 受信任查询代理通过 DuckDB 提供分析访问。

全量文件的约束验收需要实现对应适配，并先与 PostgreSQL 小样结果对照。报告没有假定两种引擎的 SQL、权限和类型行为完全相同。

### 2. 数据直接服务于课程里的岗位与任务

方案设计了八个经营或数据异常场景，以及三十道绑定权限、时点、指标口径和结果形态的 Agent 评测题。

覆盖的工作包括：

| 使用者         | 典型任务                                         |
| -------------- | ------------------------------------------------ |
| 集团经营负责人 | 月度经营总览、同比、预算达成、渠道和区域贡献     |
| 市场负责人     | 活动表现、ROAS、转化漏斗、报告完整性             |
| 区域负责人     | 门店表现、缺货、退货与库存风险                   |
| 商业分析师     | 跨期对账、库存周转、复购、归因与经营拆解         |
| 数据团队       | 定时看板、数据水位、延迟告警、质量监测和结果重述 |

每道评测题都说明需要哪些表和字段、应按什么粒度聚合、采用哪个历史时点，以及应输出什么图表或表格。正式数据生成后，再独立计算数值金标。
